LLM inference: a beginner’s guide

Anirban Bhowmick · 29 Oct 2026 · Machine Learning, LLM, Inference

What happens when you send a prompt to a large language model, what makes it fast or slow, and how engineers split the work across GPUs. No background assumed.

1. How a model produces text

An LLM reads and writes tokens (word pieces, roughly ¾ of a word each). It writes one token at a time: it looks at everything so far, picks the next token, adds it to the text, and repeats. Using a trained model like this is called inference, as opposed to training.

“Looking at everything so far” is done by attention. Every token becomes three vectors: a Query (what am I looking for?), a Key (what do I contain?) and a Value (what do I hand over if chosen?). The newest token’s Query is matched against the Keys of all earlier tokens, and their Values are blended into the result.

2. Prefill and decode

Every request has two phases with very different needs. Most serving tricks target one of them.

Prefill

Reads your whole prompt at once, in parallel. Lots of arithmetic on big matrices, so it is compute-bound. It decides how long you wait for the first token.

Decode

Writes the answer one token per step. Each step must re-read all the model weights and the stored history from GPU memory but does little math, so it is memory-bandwidth-bound. It decides how fast text streams.

3. Measuring speed: latency and throughput

TTFT
Time to first token: queueing plus prefill. Grows with prompt length and load. Drives how responsive a chat feels.
TPOT / ITL
Time per output token (inter-token latency). About 25–50 ms feels like fast streaming. Its inverse is tokens per second for one user.
End-to-end latency
≈ TTFT + TPOT × (output tokens − 1). What matters for non-streaming calls and agents.
Throughput
Total tokens per second the whole system produces for all users together. It sets your cost per token.
Goodput
Throughput that still meets your latency targets (SLOs). High raw throughput is worthless if most requests are too slow.
P50 / P95 / P99
Percentile latencies. Averages hide slow outliers, so set targets on P95 or P99.

The central trade-off

Running many requests in one batch shares each expensive weight read across all of them, so throughput goes up. But each request now waits for a bigger step, so latency goes up. Most inference tuning is choosing where to sit on this curve.

4. The KV cache

Why it exists

Look at the earlier tokens’ Keys and Values: they never change once computed. If the model recomputed them for every new token, generating a 500-token answer would repeat the same work hundreds of times. The KV cache stores each token’s Key and Value in GPU memory the first time, so every later step only computes the newest token and reads the rest. Think of keeping notes instead of re-reading the whole book before each new sentence.

Without a cache

Each step recomputes every earlier token again, so work piles up.

With a cache

Each step computes one new token and reuses the rest.

The catch: it uses lots of memory

The cache grows with every token, in every layer, for every user in the batch. For a 13B-class model it is about 0.8 MB per token, so one 2,000-token chat holds roughly 1.6 GB. Serve dozens of users and the cache can outgrow the model weights. Whatever memory the weights leave over decides how many users you can serve at once.

How older servers wasted it

Nobody knows an answer’s length in advance, so older systems reserved one contiguous block per request sized for the maximum. Most requests use far less, leaving reserved-but-empty gaps. Measurements showed 60–80% of cache memory wasted.

PagedAttention (vLLM)

vLLM copies an idea from operating systems: split the cache into small fixed-size blocks (say 16 tokens), hand them out only when needed, and keep a block table per request that maps its tokens to wherever its blocks happen to sit. Blocks need not be neighbours, so nothing is stranded.

Hatched cells are reserved but never used.

Paged blocks on demand

Each request’s blocks are scattered, only the last block is partly empty, and dashed cells stay free for new requests.

Benefits: near-zero waste, larger batches (about 2–4× the throughput in the original paper), and sharing. Requests that start with the same system prompt can point at the same physical blocks; if one later diverges, only that block is copied (copy-on-write). This is prefix caching, which also saves the compute of re-reading that shared prompt.

Making the cache smaller

GQA / MQA
Several attention heads share one set of Keys and Values, shrinking the cache a lot with little quality loss.
Cache quantization
Store K and V in 8-bit instead of 16-bit: half the memory, more room for batch.
FlashAttention
Computes attention in tiles inside fast on-chip memory, avoiding big temporary reads and writes.

5. Splitting a model across GPUs

A 70B-parameter model in 16-bit needs about 140 GB for weights alone, more than any single GPU holds. And even when a model fits, you may want more speed. So the work is divided. The main ways differ in what gets divided and how much talking the GPUs must do.

Tensor parallelism (TP): split each layer

Each big weight matrix is cut into slices, one per GPU. Every GPU computes its slice for the same token at the same time, then they combine partial results with an all-reduce (a fast sum across GPUs), about twice per layer. Attention heads are simply divided among GPUs too.

Lower latency per token and less memory per GPU, but heavy traffic: use it inside one machine with fast links such as NVLink.

Pipeline parallelism (PP): split by layers

GPUs take consecutive groups of layers, like stations on an assembly line. Only the small hidden-state result is passed along, so traffic is light and it works across machines. It does not make one token faster (it still passes through every layer), and with few requests some stations sit idle, called bubbles. Keep several requests in flight to stay busy.

Expert parallelism (EP): for Mixture-of-Experts

MoE models contain many small “expert” networks, and a router sends each token to only a few. Experts are spread over GPUs, and tokens travel to the right GPU and back (an all-to-all). Risk: popular experts become overloaded hot spots.

Sequence / context parallelism

For very long prompts, the sequence itself is divided: each GPU holds a chunk of the tokens and, in Ring Attention, passes Key/Value chunks around a ring while attention is computed piece by piece. It helps most with long-context prefill. (Sequence parallelism in Megatron is a related memory-saving trick for the non-attention parts.)

Data parallelism (DP): copy the whole thing

Run several identical replicas of the model and spread requests across them. It adds throughput, not capacity for bigger models, and needs no GPU-to-GPU talk between replicas.

Disaggregated serving

Since prefill is compute-bound and decode is memory-bound, some systems run them on separate GPU pools with different settings each, and ship the KV cache from the prefill pool to the decode pool.

Rule of thumb

Use the smallest split that fits. Tensor parallel inside a node, pipeline across nodes, replicas for throughput. With GQA, the number of KV heads caps how far TP is useful. Quantizing to FP8 or INT4 can let a 70B model fit on one or two GPUs, avoiding splits altogether.

9. Handy formulas

  • KV bytes per token = 2 × layers × KV heads × head dim × bytes per valueThe 2 is for Keys and Values. Multiply by tokens and by concurrent users.
  • Weight memory ≈ parameters × bytes per parameter70B: about 140 GB at FP16, 70 GB at FP8, 35 GB at INT4.
  • Single-user tokens/sec ≲ memory bandwidth ÷ bytes read per stepRough ceiling, since each step reads about all weights once.

Figures such as streaming speeds and memory sizes are typical guidance; measure on your own hardware and workload.
