LLM Evaluation: A Field Guide

Everything an engineer needs to run, read, and argue about LLM evaluations. Each section explains a concept, shows where it bites in a real stack, and then lists the pitfalls.

Examples throughout come from two real codebases I have worked with: an eval suite runner built on EleutherAI's lm-evaluation-harness (lm-eval), and a static dashboard that aggregates scores across a post-training chain for a reasoning MoE (mid-train → SFT → DPO → RLVR → OPSD → soup → RLHF).

1What evaluation actually measures

An eval score is a measurement. The instrument is a dataset plus a prompt, a decoding setup, an answer extractor and a metric. The object being measured is the model. Change any part of the instrument and you get a different number.

The measurement equation

score = Metric( Extract( Model( Prompt( Dataset ), Decoding ) ), Reference )
        ± sampling error (finite n)   ± run noise (temperature, non-determinism)

Most mistakes in LLM evaluation come from forgetting one of these terms. Typical cases: comparing two scores produced with different Prompt or Extract steps, ignoring the ± terms, or averaging scores produced by different Metrics.

What you can measure

Capability

Knowledge (MMLU, GPQA), reasoning (ARC, BBH), maths (GSM8K, AIME), code (HumanEval, LiveCodeBench, SWE-bench), tool use (BFCL, τ²).

Alignment / helpfulness

Instruction following (IFEval), chat quality (MT-Bench, AlpacaEval, Arena-Hard), usually scored by a judge model.

Safety

Harmful compliance (attack success), over-refusal, toxicity, dangerous knowledge (WMDP), reward-hacking probes.

Efficiency

Tokens per answer, latency, throughput, € per benchmark point. These matter a lot for reasoning models (see the efficiency page of our post-training dashboard).

Three families of scorers

ScorerHowStrengthWeakness
Reference-basedCompare to gold: log-likelihood ranking, exact match, F1, unit testsCheap, deterministic, reproducibleFormat-sensitive; only works where a single right answer exists
Model-basedJudge LLM or classifier (BERTScore, toxicity classifier, GPT-style judge)Handles open-ended outputsThe judge has its own biases and variance
HumanRaters, pairwise arenasThe ground truth for "is it good?"Slow and expensive; rater agreement is often low
Mental model

For every number, ask four questions. (1) What exactly was the model asked? (2) How was the answer extracted? (3) How many items was it scored on? (4) Was it compared with other models on the same items under the same settings? If you cannot answer all four, the number is anecdotal.

2lm-evaluation-harness anatomy

lm-eval turns a dataset into requests, sends them to a model backend, then filters and scores the responses and aggregates the scores into groups. Every task is a YAML file, sometimes with a small utils.py alongside.

  data_files:

Two things to notice. First, doc_to_choice uses the answer texts, not letters. The model is scored on the log-probability of the full answer text after "Antwort:", which is a cloze-style formulation with an MC-style prompt. Second, resolve/main is not pinned to a revision, so if the dataset repo changes, the test set changes with it.

What does doc_to_target returning -1 do?
The target index is invalid, so the doc either errors or is always scored wrong, depending on the lm-eval version. It is a silent failure mode. A preflight validation pass that counts invalid targets before spending GPU hours should fail loudly.

3The request types and why they matter

The single most important design choice in a benchmark is whether the model ranks given answers (log-likelihood) or writes its own answer (generation).

3.1 multiple_choice / loglikelihood

For each choice c, lm-eval computes log P(c | context) as a sum of token log-probabilities and picks the highest. Nothing is generated, so the result is deterministic and cheap. It does not test whether the model could produce the answer.

  • acc: argmax of the raw summed log-probability. This is biased toward short choices, since fewer tokens means fewer negative terms in the sum.
  • acc_norm: argmax of the log-probability divided by the character length of the choice. This is the standard metric for HellaSwag and ARC, and it is what our task registry picks for them.
  • acc_mutual_info: subtracts the unconditional log P(c), which calibrates away the prior of each choice.
⚠ Pitfall — whitespace at the context/continuation boundary

lm-eval builds context + target_delimiter + choice. If the context ends in a space ("Antwort: "), lm-eval moves the trailing space into the continuation so tokenisation stays natural. But a prompt that ends in a space and a delimiter of " " produces double spaces. Tokens such as " B" vs "B" have very different probabilities. One of our German tasks ends its prompt in "Antwort: ". Check the logged samples (--log_samples) to see exactly which strings were scored.

3.2 Three formulations of the same question (OLMES)

Our suite ships MMMLU-DE in three formulations. This matters because small models often score near chance on MC but well above chance on RC.

VariantScored continuationBest for
_mc (multiple choice)" A" / " B" … after listing optionsLarger models that have learned the letter format
_rc (cloze / ranked classification)The full answer text, no options listedSmall or early checkpoints; gives a smoother learning-curve signal
_bpb (bits-per-byte of the gold answer)Only the gold answer, normalised per bytePre-training ablations: continuous and low-noise

OLMES (Gu et al., 2024) reports both MC and RC and takes the max per model. Our generative-track suite configs currently reference none of these variants.

3.3 generate_until

The model writes text until a stop string or max_gen_toks. Then filters extract an answer and metrics compare it with the gold answer. This is the only meaningful mode for chat, reasoning and tool-use models, and our post-training dashboard uses it exclusively.

Field note — the stop-string bug that zeroed a BLEU score 
generation_kwargs:
  # Explicit empty `until`: without it lm-eval silently defaults to
  # fewshot_delimiter "\n\n" as a stop string, truncating multi-paragraph
  # summaries at the first blank line (cause of the bleu=0.0 anomaly).
  until: []
  max_gen_toks: 49152

A good catch. Generalise it: for every generative task, inspect at least 20 logged samples and check whether outputs end where they should.

Field note — strict vs flexible extraction 
filter_list:
  - name: "strict-match"
    filter:
      - { function: regex, regex_pattern: "(?:Die Antwort ist|The answer is) (\\-?[0-9\\.\\,]+)" }
      - { function: take_first }
  - name: "flexible-extract"
    filter:
      - { function: regex, group_select: -1, regex_pattern: "(-?[€$0-9.,]{2,})|(-?[0-9]+)" }
      - { function: take_first }
metric_list:
  - { metric: exact_match, regexes_to_ignore: [",", "\\$", "€", "\\.$"] }

Strict measures format compliance and correctness together. Flexible takes the last number and approximates correctness alone. A large gap between them means the model is right but ignores the format. Report both and understand the gap.

German-specific pitfall: removing "," treats the German decimal comma as noise. "1,5" becomes "15", and "1.000" (German thousands) stays "1.000", which no longer matches "1000". Normalise numbers with a locale-aware parser instead of regex deletion.

3.4 loglikelihood_rolling

Perplexity over a whole document. Bits-per-byte = total NLL (nats) / (ln 2 · bytes) is tokenizer-independent. Use it to compare models with different vocabularies; never compare raw per-token perplexities across tokenizers.

A base model scores 26% on MMLU-DE _mc and 41% on _rc. Is it bad at knowledge?
Not necessarily. 25% is chance for 4 options, so on _mc it has probably not learned to map content to letters. The RC score shows it does prefer the correct answer text. Report RC for early checkpoints and switch to MC once the model is clearly above chance.

Field note — routing by request type (a strong pattern)

Our wrapper resolves each requested group to its leaf tasks, partitions them by output_type, and builds an invocation_plan.json. Generation goes to the chat API and log-likelihood goes to a raw-completions profile pinned to apply_chat_template: false. Generation runs first, so cheap results are saved before long MC runs. The split results are then merged back together.

This is a good engineering design. It has one statistical consequence: the same MC task scores differently depending on which path ran it.

⚠ Pitfall — the chat template changes log-likelihood scores

With apply_chat_template: true (our base config turns it on for vllm), the MC context is wrapped as a user turn plus the assistant header. The answer is then scored at the start of an assistant turn, where the model expects "Sure! …" or <think>, not " Paris". Through the raw-completions API the same task runs without a template. Never compare MC numbers across these two paths. Store apply_chat_template next to every score, and pick one convention per benchmark family (the common choice: no template for log-likelihood, template for generation).

Things to put in model_args deliberately

  • dtype (bf16 vs fp16 vs fp8 quantisation changes scores, usually by <1pp, sometimes more for reasoning)
  • max_length: context truncation silently cuts off long few-shot prompts on the left
  • tensor_parallel_size, gpu_memory_utilization: speed only, but batch composition can change floating-point results
  • Adapters: our wrapper silently ignored PEFT adapters for vllm and API backends — a bug worth failing loudly on. Merge LoRA weights before evaluating, or raise an error.

5Prompting choices

Prompt format alone can move MC accuracy by 5–10pp on small models (Sclar et al., 2023, "Quantifying LMs' sensitivity to spurious features in prompt design"). Treat the prompt as part of the benchmark definition.

Few-shot vs zero-shot

  • Base models: few-shot (typically 5 for MMLU, 8 for GSM8K CoT) shows them the format.
  • Chat / reasoning models: zero-shot with the chat template is how they are actually used. Our dashboard uses 0-shot everywhere.
  • fewshot_as_multiturn: presents each shot as a user/assistant turn pair instead of one long user message. It matters when apply_chat_template is on. Our base config's comment says it defaults on together with the chat template — check the behaviour of your installed lm-eval version and log the effective value.
  • num_fewshot: null in a base config means "use each task's own default". That is fine, but record the effective n-shot from results_*.json in every summary.

Thinking models

Reasoning models (Qwen3, gpt-oss, our own checkpoints) emit <think>…</think> before the answer. Consequences:

  • Token budget: too small a max_gen_toks cuts off the reasoning, so no answer is produced and the item is scored wrong. Our configs ship 49,152-token budgets in some places and 131,072 in others. A truncation rate above about 1% means the budget, not the model, sets the score.
  • Strip the think block before extraction, or the regex may pick a number from the reasoning.
  • enable_thinking: false via chat_template_kwargs: some of our task YAMLs set it with "REMOVE for hf/vllm" comments while the backend was vllm. The logs filled with hundreds of "API returned null content" warnings. Null outputs are scored as wrong, or as non-toxic in the toxicity task, which inflates safety.
⚠ Pitfall — format artefacts that differ between languages

One of our German ARC task sanitisers prefixes every choice with "Option: " (and empty choices become "Option: (leer)"). The English ARC tasks have no prefix. Any "EN vs DE gap" on ARC therefore mixes language ability with a format change. Fix: apply the same sanitiser to both languages, or only substitute empty choices.

Your GSM8K-DE score drops 12pp after switching from vllm to the chat API. Name three suspects.
(1) The chat template or few-shot-as-multiturn changed the prompt. (2) Thinking was enabled on one path, so the budget truncated or content came back null. (3) Stop strings ("Frage:", <|im_end|>) behave differently when the server applies the template. Diff the logged samples for the same doc_id before blaming the model.

The unbiased pass@k estimator (Chen et al., 2021)

Generate n ≥ k samples per problem and count c correct:

pass@k = 1 − C(n−c, k) / C(n, k)       # averaged over problems

import numpy as np
def pass_at_k(n, c, k):
    if n - c < k: return 1.0
    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

Answer extraction for maths

We score AIME with math_verify. It parses \boxed{…} and compares the answers symbolically (so 1/2 = 0.5 = \frac{1}{2}). String exact-match on maths underestimates strong models, and the size of the error grows with how creatively the model formats its answers.

⚠ Pitfall — the rouge_score tokenizer and German

Google's rouge_score default tokenizer lowercases and replaces every non-[a-z0-9] character with a space. "Gemäß" becomes "gem ß"… and the umlauts are gone. One of our public-sector summarisation tasks uses it without a custom tokenizer. For German, pass a whitespace or Unicode-aware tokenizer (RougeScorer(..., tokenizer=...)) or use a multilingual implementation.

7Evaluating post-training

Post-training evaluation answers a different question from pre-training evaluation. The question is not "how much does the model know" but did this stage help, what did it cost, and what did it break?

Our dashboard's evaluation paradigm

  • Generation only. No log-likelihood scoring and no acc_norm. A reasoning model's log-probabilities over answer letters do not reflect how it is used.
  • Sampling: temperature 0.6, top_p 0.95 (the vendor-recommended settings for reasoning models; greedy decoding often loops), 0-shot, no system prompt, think template.
  • Repeated rollouts for small benchmarks: AIME avg@8, code pass@10.
  • Agentic and tool use: BFCL (AST and executable matching), SWE-bench (resolve rate), τ² (pass^1).
  • Safety as higher-is-better: 1 − ASR, 1 − over-refusal, and WMDP shown as 1 − acc (so lower dangerous knowledge counts as better).
  • Reward-hacking probes: hack resistance on SLR-Bench, ImpossibleBench rates conditioned on solved problems. Checking for reward hacking is essential after RLVR.
  • Per-model exceptions ledger: e.g. repetition_penalty 1.1 for models that loop. Being transparent about these is excellent practice, but every exception is a confounder.
✓ Good practice in the dashboard

Several things are worth copying: an explicit defined set of benchmarks per track, so missing cells are not averaged away; display-only rows for contaminated or inverted benchmarks (GPQA, WMDP); hatched "not run" vs ⊘ "skipped on purpose" cells; and matched EN–DE pairs for language-gap claims.

What to look for when evaluating a stage

  • Alignment tax: RLHF or DPO raises chat and win-rate scores but lowers maths and code. Always show the capability and helpfulness deltas side by side.
  • Verbosity drift: RL tends to lengthen answers. Plot score against tokens per answer (the dashboard's token-vs-score Pareto). A gain bought with 3× the tokens may not be worth deploying.
  • Reward hacking: rising verifiable-reward benchmarks together with falling hack-resistance or IFEval strict scores.
  • Safety regressions: over-refusal and attack success both move after DPO. Report both directions.
  • Soups: a weight average should sit on or above the line between its parents. If not, the checkpoints are in different basins.

8LLM-as-a-judge

Judges make open-ended evaluation scalable. They are also a second model with its own biases, so treat the judge as an instrument that needs calibrating.

Single-answer grading

Score each response on a 1–10 scale (MT-Bench). Simple, but scores drift with the judge's mood and prompt; resolution is poor near the top.

Pairwise comparison

"Which response is better, A or B?" against a fixed baseline (AlpacaEval, Arena-Hard). More reliable; outputs a win rate.

Known judge biases & mitigations

BiasMitigation
Position bias (prefers the first answer)Judge both orders; count inconsistent pairs as ties
Verbosity / length biasLength-controlled win rate (AlpacaEval LC: a GLM regresses out the length difference); style control (Arena)
Self-preference (judge favours its own family)Use a judge from a different family from the evaluated models; cross-check with a second judge
Grader deviation from the official protocolUse the official judge prompt and classes; otherwise label the score "-like"
Run-to-run varianceRepeat judging ≥3×, report mean ± std; use temperature 0 for the judge where possible
Field note — judges in our dashboard
  • AlpacaEval LC is judged locally by Qwen2.5-32B; Arena-Hard v2 and SimpleQA by a Qwen3-27B-class model. These are not the official judges, so the absolute numbers are not comparable with public leaderboards. Relative rankings within our board are still valid.
  • SimpleQA uses a binary prompt instead of the official 3-class grader (correct / incorrect / not attempted). This merges "abstained" into "wrong", which removes the calibration signal that SimpleQA was designed to measure.
  • MT-Bench 1–10 is stored ×10 so it fits the 0–1 board. This is fine, but a 1–10 score of 1 maps to 0.1, not 0, so its floor is not comparable with accuracies.
  • Vibe check: 112 prompts, 5 judge runs, mean ± std. This is the only place in the dashboard with an error bar, and the judge itself warns of 16–60% swings. Some hard-coded fallback numbers in the page's JavaScript are stale compared with the live judge summary.

How to validate a judge (do this once per judge × task)

  1. Have humans label 100–200 pairs.
  2. Measure judge–human agreement (Cohen's κ, or accuracy on non-tie pairs) and judge–judge agreement across two runs.
  3. Swap positions and measure the inconsistency rate.
  4. Correlate win rate with response length. If ρ > 0.5, length control is mandatory.

9Statistics & error bars — the expert's edge

Most published LLM comparisons are inside the noise. The engineers who know how large the noise is make far fewer wrong calls. Required reading: Miller (2024), "Adding Error Bars to Evals".

9.1 Standard error of an accuracy

SE = sqrt( p · (1 − p) / n )          95% CI ≈ p ± 1.96 · SE

Try n = 30 (AIME): at p = 0.5, the 95% CI is ±18pp. Even with avg@8 rollouts this shrinks only a little, because the uncertainty comes mainly from which 30 problems were chosen, not from sampling. MT-Bench with n = 80 gives roughly ±11pp on a binary-equivalent scale. A dashboard that prints ±0.1pp deltas on these benchmarks is showing noise.

9.2 Comparing two models: use paired tests

Both models answer the same questions, so their errors are correlated. The paired standard error is much smaller than the unpaired one:

d_i  = score_A(i) − score_B(i)           # per item, from --log_samples
Δ    = mean(d_i)
SE_Δ = std(d_i, ddof=1) / sqrt(n)        # paired SE
# Unpaired (wrong for same-item comparisons): sqrt(SE_A² + SE_B²)
# For binary outcomes the paired version is McNemar's test.

Minimum detectable effect at 80% power and α = 0.05 is about 2.8 · SE_Δ. On a 1,000-item benchmark with ~15% disagreeing items, the MDE is about 2pp. On AIME it is more than 15pp.

9.3 Clustered questions

If items come in clusters (several questions on one passage, or 57 MMLU subjects), they are not independent. Use clustered standard errors or a cluster bootstrap. Naive SE underestimates the error, by 3× in some reading-comprehension sets according to Miller (2024).

9.4 Combining standard errors across subtasks

# Mean of K independent subtask scores, equal weights:
SE_mean = sqrt( Σ SE_k² ) / K            # NOT mean(SE_k)
# Weighted:  SE = sqrt( Σ w_k² · SE_k² )  with Σ w_k = 1
# Or: bootstrap — resample items within each task, recompute the full aggregate, take percentiles.
⚠ Field note — the mean-of-standard-errors bug 
"stderr": float(fmean(stderrs)) if stderrs else None,

This one line, in two places of our aggregation code, computes a group's stderr as the mean of the subtask stderrs. For K subtasks, the mean of their SEs overestimates the SE of their mean by about √K. Use the formula above. Category and overall scores had no SE at all. Our exported results contained no SEs either, and 42 of 151 tasks had n: null, so not even a binomial SE could be reconstructed.

9.5 Run-to-run noise

With temperature 0.6, rerunning the same model gives a different score. Estimate this once per benchmark: run 3–5 seeds and compute the std. A difference between checkpoints smaller than 2× the seed std is not evidence of anything. For checkpoint selection, prefer benchmarks with high signal-to-noise (spread between models ÷ seed noise). This is the OLMo / DataDecide approach for choosing evals.

Checkpoint B beats A by +1.2pp on a 500-item benchmark (both ~70%). Report it?
Unpaired SE ≈ √(2·0.7·0.3/500) ≈ 2.9pp, so the 95% CI of the difference is about ±5.7pp unpaired. A paired test may shrink this to around ±2–3pp, which still contains 0. Report "no significant difference", or collect more items or seeds.

10Aggregation & leaderboards

An "overall score" is an opinion expressed as arithmetic. Make the opinion explicit: what is the denominator, what are the weights, and are the scales the same?

10.1 The denominator rule

Two models can only be compared on the intersection of the benchmarks they were both evaluated on. Averaging each model over "whatever it has" turns differences in coverage into apparent differences in capability.

Field note — a real example

In our dashboard, one RLVR checkpoint scored on 171 benchmarks against an SFT stage scored on far fewer reads +0.5 on its own coverage and −5.1 on the 114 benchmarks the whole chain shares. Same checkpoint, opposite conclusions. Elsewhere a mid→final delta read +25.4pp on own coverage instead of the true +7.4pp.

The default comparison view still showed each model on its own coverage. Make the shared basis the default for any view that ranks models or shows deltas.

10.2 Flat vs hierarchical (balanced) means

Flat (micro over tasks)

One mean over all benchmarks. Large families dominate: about 54 multilingual variants weigh 54× as much as SWE-bench.

Balanced (hierarchical)

benchmark → category → supergroup → overall. Each capability gets equal weight, but every task must belong to exactly one leaf of the hierarchy.

⚠ Field note — membership bugs that silently re-weight the overall
  • Double counting: one of our supergroups contains multi_turn, but only multilingual/german are listed in its cross-cutting set. MTBench (also chat) and BFCL multi-turn (also agentic_code) are therefore counted twice in the Balanced overall. longctx and translation deserve the same audit.
  • Silent drops: 33 tasks had a cat value missing from their category list (e.g. a Spanish AIME variant tagged math but listed under [multilingual]). Aggregation used the list, so these dropped out of Balanced but counted in Flat.
  • Orphans: six scored tasks (HellaSwag and three TruthfulQA variants among them) had no entry in the task registry at all and were silently ignored.

Fix: a unit test asserting that every scored task belongs to exactly one non-crosscut leaf (or is explicitly excluded), and that every category value is registered.

10.3 Never average different scales

⚠ Field note — the ">1 means percent" heuristic 
def _normalize_for_harmonized_mean(score: float) -> float:
    return score / 100.0 if score > 1.0 else score

A BLEU of 0.8 on a 0–100 scale stays 0.8 and is read as 80%. A GermanQuAD F1 of 0.9 (0–100 scale) also stays 0.9. Rescaled BERTScore can be negative. The resulting category mean combines accuracy, BLEU-acc, BERTScore and 1 − toxicity. Fix: declare each metric's scale and chance level in a registry, and normalise explicitly.

10.4 Normalise for chance

A 4-way MC task has a 25% floor and a free-form maths task has a 0% floor. Averaging raw scores rewards tasks with a high floor. The HF Open LLM Leaderboard v2 approach rescales each task with (score − chance) / (1 − chance) before averaging.

10.5 Alternatives to a single mean

  • Mean rank / win rate across tasks (HELM): robust to scale, but depends on which models are on the board.
  • Bradley–Terry / Elo over pairwise battles (Chatbot Arena), with bootstrap CIs.
  • Pareto frontiers (score against cost or tokens) instead of a single ranking. Our efficiency page does this well.

11Contamination & data hygiene

If test items, or close paraphrases, were in the training data, the benchmark measures memorisation.

Detection techniques

  • n-gram overlap (e.g. 13-gram) between the training corpus and test items: the GPT-3 / Llama approach. lm-eval's should_decontaminate + doc_to_decontamination_query only marks the query; you still have to run the overlap pipeline.
  • Perturbation tests: rephrase or renumber items (GSM-Symbolic, GSM8K-Platinum) and see whether accuracy drops.
  • Min-K% probability and similar membership-inference signals.
  • Time-split benchmarks (LiveCodeBench, AIME by year): only count items published after the training cutoff.
Field note — what this looked like in our stack
  • Dashboard: contaminated GPQA is display-only, kept out of averages. Good.
  • Two internal tasks evaluate on the train split; one test set is LLM-generated and LLM-filtered (so it is biased toward models similar to the generator); another use-case set is 20 pairs from the same family as the SFT data. Label these as in-distribution checks, not held-out evals.
  • Datasets loaded from resolve/main without a revision: pin revision=<commit> so the test set is fixed.

12Reproducibility & operations

What every result file should carry

  • Model ID and revision or hash, adapter, dtype or quantisation
  • lm-eval version (one of our environments pinned 0.4.13 while another had 0.4.11 — and task defaults change between releases), backend, vllm version
  • Effective prompt settings: chat template, few-shot count, fewshot_as_multiturn, gen_kwargs, think on/off
  • Seeds (--seed), limit, dataset revisions
  • Logged samples (--log_samples). Our wrapper always passes this, which is excellent: it enables paired tests and error analysis.
⚠ Field note — smoke runs overwrite full runs 
limit: 10 # set null for entire dataset

This was our committed default: 10 documents per task. The output folder hash covered only model and adapter, and the summary read the newest results_*.json. So a smoke run after a full run replaced its numbers in the summary without any warning. Fixes: default limit: null; include limit, backend and chat-template settings in the run hash; refuse to summarise results that have limit set unless a --smoke flag is given.

⚠ Field note — no seed, no gen_kwargs

Our command builder never passed --seed or --gen_kwargs. lm-eval has default seeds, but API backends are non-deterministic anyway. Pass the seed explicitly and record it. Make decoding settings explicit per suite instead of per task YAML. For example, one summarisation task set top_p without temperature.

Operational patterns worth keeping

  • A preflight check: validates MC docs and tokenises continuations the way lm-eval does before GPU hours are spent.
  • An invocation plan plus the exact command files: a precise record of what ran.
  • Suite configs with base_config: inheritance and pydantic validation.
  • A SLURM suite runner + smoke runner. Ordering suites from cheap to expensive surfaces failures early.
  • API client hardening (timeouts, backoff).

Efficiency is part of the evaluation

For reasoning models, report tokens per answer and cost next to accuracy. Our dashboard's efficiency page and token-vs-score Pareto do this. But check the constants: at one point the same page used 240 W in one place and 200 W in another for the same hardware. Constants deserve the same review as scores.

13Multilingual & German evaluation

  • Machine-translated benchmarks (MMLU-X, ARC-X, HellaSwag-X, GSM8K-X, TruthfulQA-X from OpenGPT-X) carry translation errors, cultural mismatch (US law in MMLU), and formatting artefacts (the "Option: " prefix, "(leer)" placeholders, "Choice: (empty)" padding).
  • Language-gap claims need matched pairs: the dashboard's EN–DE comparison only pairs benchmarks that exist in both languages and requires at least eight of them. This is the right approach.
  • Native German benchmarks carry more weight than translations: GermanQuAD, EUR-Lex-Sum DE, public-sector tasks, GermanPartiesQA.
  • Tokenizer fairness: German produces more tokens per word with English-centric tokenizers. Token budgets truncate German answers earlier, and per-token perplexity is not comparable across languages (use bits-per-byte).
  • Metrics: use Unicode-safe tokenisation (ROUGE), locale-aware number parsing (decimal comma), and language-appropriate classifiers (toxicity).
Field note — GermanQuAD & GermanPartiesQA
  • GermanQuAD's custom task.py hardcodes its own generation kwargs, so the YAML generation_kwargs are ignored (the logs showed a 256-token / "\n\n" default). No-answer detection is a substring check for "unanswerable", which a German-answering model will never write.
  • GermanPartiesQA uses English labels in a German prompt, ends with "Antwort: " (trailing space), and has no calibration. Party-alignment scores are therefore sensitive to the prior of each label. Consider acc_mutual_info or permuting the label order.

15Expert checklist & learning roadmap

Pre-flight checklist for any eval run

  • Benchmark set fixed in advance (a defined set per track), dataset revisions pinned
  • Prompt convention decided: chat template, few-shot count, multiturn, think on/off
  • Token budget large enough: truncation rate < 1% on a pilot run
  • Extraction verified on 20 logged samples per task (strict vs flexible gap understood)
  • Metric scale, chance level and direction registered for every task
  • limit = null, seed set, versions recorded, --log_samples on
  • Comparisons on a shared item set; paired SE or bootstrap CI reported
  • Seed noise known for each benchmark used in checkpoint selection
  • Judges: official prompt (or labelled), both orders, length control, ≥3 runs
  • Aggregation invariants tested (no double counting, no orphans, values in range)
  • Contamination status noted per benchmark; train-split checks labelled as such

Roadmap to expertise

  1. Week 1: mechanics. Write one MC task and one generative task from scratch in lm-eval. Run them with hf and vllm, diff the logged samples, and explain every difference.
  2. Week 2: statistics. Using --log_samples from two of your checkpoints, compute paired bootstrap CIs per task and for the overall score. Find out which of your dashboard's deltas survive.
  3. Week 3: sensitivity. Rerun MMLU-DE with 3 prompt formats × MC/RC. Measure the spread, and compare it with the gaps between models.
  4. Week 4: judges. Label 100 Arena-Hard-style pairs yourself and measure κ for your judge model, the position bias and the length correlation.
  5. Ongoing: follow new benchmark releases and their contamination status; read leaderboard methodology changes (the HF Open LLM Leaderboard v2 write-up is a good example).

16Glossary

acc_norm
Accuracy using log-probability normalised by the character length of each choice.
avg@k
Mean accuracy over k sampled rollouts per item.
Bits-per-byte (BPB)
Negative log-likelihood normalised per UTF-8 byte; comparable across tokenizers.
Cloze / RC formulation
Scoring the answer text itself without listing the options.
Contamination
Test items present in the training data.
Filter
lm-eval post-processing that turns raw generations into answers (regex, take_first, majority_vote).
LC win rate
Win rate against a baseline with the effect of response length regressed out.
MDE
Minimum detectable effect: the smallest true difference a test reliably detects (≈ 2.8 · SE at 80% power).
OPSD
On-policy self-distillation: a post-training stage in our pipeline.
Paired test
A comparison using per-item differences between two models on the same items.
pass@k
Probability that at least one of k samples is correct (unbiased estimator by Chen et al.).
RLVR
Reinforcement learning with verifiable rewards (unit tests, maths checkers).
Soup
A weighted average of model weights from several checkpoints.
Strict vs flexible match
Extraction that requires the prescribed answer format vs extraction of the last plausible answer.
